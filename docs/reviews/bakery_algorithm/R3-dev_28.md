# R3 review: bakery_algorithm, Dev (28)

Verdict: I could implement this lock from the video and I'd get it right. There are no blockers. Three findings would change what I take away: the Arm half of the 12_7 measured table works against the voice; indentation is stripped from both on-screen code snippets; and nobody ever says on screen why production code uses the magic sign instead.

## Comprehension check

- **01:** `x = x + 1` is two steps, read then write. Of the 6 orders of two programs doing it (C(4,2)), the 4 where both read before either writes lose a point. A fix has to work in every order, not only in the likely ones.
- **02:** A check-then-flip "vacant" sign is itself a race (8 of 14 orders put both inside). Dijkstra's spec asks for three things: never two inside, idle processes block nobody, and no timing assumptions. Knuth added that everyone eventually gets in. Hardware cheats with an atomic check-and-flip. The open question is what happens if a read can catch a half-written value.
- **03:** Each customer owns a slate that only she writes. She reads every other slate once, writes max + 1, and waits for every smaller ticket. There is no shared ticket machine, and nobody writes anyone else's memory.
- **04:** Concurrent max reads can produce equal tickets. Comparing (ticket, id) like dictionary words makes the order total, and the room serves the smallest pair first.
- **05:** A ticket that has been computed but not yet written looks like "not in line". The choosing flag fixes that: raise it before reading, lower it after writing, and wait for theirs to drop before you compare. Without flags 4 of 28 orders fail; with flags none of 322 do.
- **06:** With three customers, all ~2.1 billion orders are safe.
- **07:** One four-customer run where a tie, a flag wait and a late arrival all play out. Service follows the (ticket, id) order, and 5 visits give 5 points.
- **08:** Fact one: if I finished choosing before you started, your ticket is bigger. Fact two: if I'm in the room, every other ticket holder has a bigger pair (case split on where they were at my last flag check). So two customers in the room would each be smaller than the other, which is impossible. A model check up to 4 customers agrees.
- **09:** The proof only ever trusts reads that overlap no write. So the algorithm survives "safe" memory that returns garbage mid-write; garbage only makes tickets bigger.
- **10:** Even a mid-write read of Blue's old zero is harmless, because her flag went up after Green finished choosing (fact one reversed). Lamport found this property only after writing the proof. One trap remains: reading a slate twice in the max (compare, then copy) can break it.
- **11:** The lock is first-come-first-served from the doorway, and each other customer can get ahead of you at most once after you take a ticket. The price: tickets grow while the bakery never empties (32-bit tickets overflow in ~50 days at one entry per ms, 64-bit lasts centuries), every entry makes 3(N−1) reads, and a customer frozen while choosing stalls everyone.
- **12:** Store buffers break "a finished write is seen by every later read", so both customers walk in with memory still all zeros. x86 needs two fences per entry (after raising the flag, after lowering it), and Arm reorders more. The portable fix is SeqCst on every access; acquire/release is not enough. Measured: Relaxed loses ~1–2 M points per 60 M visits, SeqCst loses 0.
- **13:** In practice people use atomic read-modify-write instructions. The bakery still runs where those don't work: Arm's TF-A firmware uses it while a core wakes with its data cache off. Its "bigger than any you've seen, ids break ties" idea comes back in Lamport clocks and in Paxos ballot numbers.

## What I checked, and how

- **Pictures.** I opened all 13 sheets with the script lines. The tiles that were too small to read (04, 10, 12) I cropped and upscaled; the 10_4 tile measured as a single flat background color. Where a 1.5 s frame can't show the payoff, I sampled the narrated watch render at points inside the line: the 12_1 card, the 12_7 panel and table, the 10_4 code, the 11_7 costs card, the end of 06_2's counter, and the 13_2 card. That render may be a little older than the current `cpu.rs`: after the table it shows the x-ray again, which the current code no longer does. I made no finding from that difference.
- **Order counts.** I recounted these with my own enumerator, written independently of `oracle.py` (every read, write and successful wait is one step; one visit each): sign 14 orders, 8 with both inside; no flag 28 / 4; flag 322 / 0; three customers 2,126,816,238 / 0. All match. C(4,2) = 6 with 4 losing, by hand.
- **Arithmetic.** 365.25 d = 31,557,600,000 ms < 2³⁵ = 34,359,738,368. 2³² ms = 49.7 d and 2³¹ ms = 24.9 d. 2⁶⁴ ns = 584.5 y and 2⁶³ ns = 292.3 y. All match the screen.
- **Code panel (12_7).** I read it line by line against Rust's rules: the `Ordering::SeqCst` variant import, the `|&j|` filter pattern, the `(u64, usize)` tuple comparison, and `{ break }` as an `if` body. As far as I can tell it compiles. I did not compile it here. `src/bin/bakery_stress.rs` has the same lines with the orderings as a type parameter, and its records exist for both CPUs. The logic matches the voice: flag up, read each slate once, write max + 1, flag down, then for each other customer wait for her flag, then for her slate to be 0 or her pair to be bigger. `(nj, j) > (t, i)` never ties, because j ≠ i.
- **Measured records.** I read both stress records. The on-screen cells match the totals: x86 Relaxed 1,006,846 / Release-Acquire 1,173,616 / SeqCst 0; Arm Relaxed 2,314,899 / Release-Acquire 0 / SeqCst 0; Arm's 100-run Release/Acquire 0 of 600,000,000. A 4-thread Arm record (Relaxed 6,694,918 lost; Release/Acquire and SeqCst 0) exists but is not on screen.
- **Ordering claims.** x86, two fences: with F1 and F2 in place, every load the lock makes runs with an empty store buffer, so TSO behaves like SC for the lock. That agrees with the on-screen model note and with Abdulla et al. SeqCst everywhere is correct by DRF-SC. Acquire/release falls short on the store→load (SB) pattern, and the x86 column confirms it. Arm (12_6) is the message-passing outcome, as sourced; the video gives no fence count for Arm and needs none, since SeqCst is the answer.
- **Unchecked** (I did not rebuild these models): 3,027,633 states (08_9), 269,550 states (09_6), the 33-step double-read trace (10_4), the 22-step reordering-outbox trace (12_6), and the 12-step TSO trace (12_3–12_4).
