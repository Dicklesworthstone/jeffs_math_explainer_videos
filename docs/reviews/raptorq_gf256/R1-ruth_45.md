## Comprehension check

| ch | the sentence I would say to a friend |
|---|---|
| 01 | A sender can't take resend requests from a million phones that each randomly lose 1% of packets. A loop of the file leaves the unluckiest phone waiting five or six loops, and random uncoded pieces are worse (about 97,876 on average for 10,000). Yet a phone holding just two packets more than the picture has pieces almost always decodes. That gap is what the video has to explain. |
| 02 | Each packet is an XOR equation over a subset of pieces, so receiving means collecting equations and decoding means solving a linear system. Only the number of useful (independent) equations matters, and a shared seed lets the sender make as many as it likes. |
| 03 | If each card includes each piece by a fair coin flip, every useful card doubles the span, so the j-th card is useless with chance 2^(j−1−K). All K cards are useful with probability ∏(1−2⁻ⁱ) → 0.2888, so exactly enough random XOR cards fail 71% of the time at any size, and almost all of that risk sits in the last few cards. |
| 04 | Each spare XOR card cuts the failure by at most a factor of 2 (about 20 spares for one in a million), and some patterns, such as a loop of pairwise XORs, are singular whatever happens. So we want cards that scale pieces by more than 0 or 1, which needs a byte multiplication we can undo. |
| 05 | Wrap-around arithmetic mod 256 has zero divisors (2·128 = 0). A random matrix over Z/256 is invertible exactly when it is invertible mod 2, so it fails the same 71%. Prime moduli give fields, but no prime has exactly 256 values, so the 256-element field must be built another way. |
| 06 | Read bytes as polynomials over GF(2) and multiply modulo an irreducible degree-8 polynomial (0x11D). The result is a field where 3·7 = 9, 2·128 = 29 and 2·142 = 1, while the reducible x⁸+1 gives 3·255 = 0. Which of the 30 irreducibles you pick is a labelling both ends must share. |
| 07 | Under 0x11D the byte 2 generates all 255 nonzero bytes, so discrete logs turn multiplying into adding clicks mod 255, and the log-sorted table is constant along anti-diagonals. Under AES's 0x11B the byte 2 only has order 51: still a field, with a different hand on its clock. |
| 08 | With uniform byte coefficients, a random card misses any fixed nonzero change with probability exactly 1/256. The union bound then gives failure below 256⁻ʰ/255 (0.39% with exactly enough), so each spare buys a factor of 256 instead of 2, and 0/1 coefficients gain nothing from the bigger field. |
| 09 | Dense elimination costs about K³/3 operations (4×10¹³ at K = 50,000), so practical codes use sparse cards and peeling. Peeling stalls without the right card and can collapse even with a few percent extra. Reed–Solomon wastes nothing, but its length is capped near the field size. |
| 10 | RaptorQ keeps every packet a sparse XOR and adds S XOR constraint rows plus 10–16 byte-coefficient constraint rows. The XOR rows stop H short of full rank, just before the danger, and the byte rows close the gap. Swapping them for XOR rows brings back 71% failure (against 0.65%). Inactivation is elimination in a good order and succeeds exactly when the system has full rank. *(I got "H short of full rank" only from the Ruth note and Table 2. The narration's "fill almost the whole space" is contradicted by the K′ = 10 grid it shows; see RB-01.)* |
| 11 | A real decoder at K = 10 over 10⁶ trials failed 6,316, 24 and 1 times at K, K+1 and K+2, in line with RFC 6330's average-case requirement (at most 10⁻², 10⁻⁴, 10⁻⁶ at the padded K′). The code sends the originals first, appears in ATSC 3.0 (its predecessor Raptor in 3GPP mobile broadcast, 2005), and RAID-6 uses the same field polynomial. |

No chapter gets a blocker on comprehension.
