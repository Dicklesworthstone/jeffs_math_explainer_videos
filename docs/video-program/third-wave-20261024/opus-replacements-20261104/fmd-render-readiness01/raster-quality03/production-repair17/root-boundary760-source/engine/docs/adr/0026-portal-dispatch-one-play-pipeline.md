# ADR-0026 — The portal plays through one pipeline; animation families register, they do not wrap

**Status:** Proposed (owner ratification required before any migration child starts; fm-5wq.15)
**Date:** 2026-09-29
**Bead:** fm-5wq.15
**Amends:** none (new decision). Applies §5 "one engine, two front doors", §15.2's method-resolution cache
rule and §16.2 "one API schema" to the portal's runtime dispatch.

## Context

The portal's `manimlib` behavior is assembled at import by stacking installers on the embedded bootstrap.
The effective dispatch table (`docs/api/portal_dispatch.tsv`, generated by
`scripts/portal_dispatch_table.py` from the live portal and drift-checked by
`portal_dispatch_table_matches_the_embedded_portal`) measures the result, at d0d648d9:

| measure | value |
|---|---|
| Python in the portal layer | 55.3k lines (bootstrap 24,669; animation semantics 2,508; `fmn_python` 28,128 in 121 modules), vs ~23.1k for the whole Reference |
| installer steps run at import | 77 (`fmn_python/initialization.py` `_STEPS`) |
| Reference methods and properties (1,454): outermost implementation | bootstrap 1,053; installers 271 (72 modules); animation semantics 59; refusing placeholders 61; native 7; stdlib 3 |
| symbols whose call passes through more than one implementation | 97 |
| `Scene.play` | 15 implementations deep: 10 installers, 4 semantics, 1 bootstrap |
| `_requires_python_animation` (routing decision) | 11 installer layers |

Each installer that wraps `Scene.play` does the same four things before delegating: normalizes `.animate`
builders to Animations (so `prepare_animation` runs up to six times per call), walks the whole animation
composition with its own seen/visiting cycle detection, selects its family (fades, movements, rotations,
indications, maintained positions...), and prepares or admits it. `_requires_python_animation` is a
parallel chain in which each family decides "native or Python" by walking the mobject family again.

What this costs, measured (calibration-unqualified, ADR-0024):

- **Per call, the wrapping itself is cheap.** Profiling 200 one-frame plays of a 50-member group, each play
  layer's own time is a few milliseconds in total. The layering is not a throughput problem.
- **The admission protocol was.** The per-member walks resolved every hook of every member through
  `inspect.getattr_static`: 27,500 calls per play, 90% of the play's time. 2997b6a1 memoized per walk:
  140 ms → 22 ms per play. That was the fourth fix of the same shape (94a49540, dc691fa6, 1a592c4f) in one
  week, each found by profiling after a corpus scene ran slow. The pattern repeats because every family
  re-implements admission.
- **Import.** Protocol tables rebuilt by each installer cost ~0.35 s of every `import manimlib` (interleaved
  A/B) until 1a592c4f.
- **Correctness and legibility.** What `Scene.play` does is the composition of ten independently written
  wrappers in `_STEPS` order. A family's cycle handling, builder normalization or admission rule can differ
  from its neighbours', and no file states the whole behavior. The layer count grew 54 → 77 steps between
  2026-09-23 and 2026-09-29.

## Options considered

**(a) Hand-migrate every family into a native (Rust) dispatch protocol now.** Choreo's lifecycle becomes
the only `play`; Python runs only for hooks a user subclass overrides. This is the end state, but done as
one migration it moves 72 installer modules' behavior into Rust at once, with no intermediate state whose
witnesses can stay green family by family.

**(b) Generate the portal class layer and its hook dispatch from the one API schema (§16.2).** It stops
growth structurally: a new method is a schema row, not an installer. It is right for signatures,
constructors and refusals (the placeholders are already schema-driven). It does not by itself say how a
play is admitted and executed, and generating behavior from a schema before that protocol exists would
freeze today's layering into generated code.

**(c) Staged: one Python play pipeline with registered families first, then move the pipeline native, then
generate the class layer.** Each stage keeps every witness suite green and is measurable.

## Decision (proposed)

Adopt (c), with (a) as stage 2 and (b) as stage 3.

1. **One play pipeline.** `Scene.play` (and `Scene.wait`) is one function. Per call it normalizes builders
   once, walks the composition once with one cycle check, and asks each registered family, in a fixed
   documented order, to `admit`, `prepare` and `finalize` the animations it owns. Then it runs the core
   lifecycle. A family is a registration (a record of hooks and the classes it claims), never a wrapper.
2. **Admission is decided once per class and walk, by construction.** The pipeline owns the family walk
   and the per-class override memo (the contract from 94a49540: valid only while no authored code runs).
   A family supplies the hook names it cares about, not a walk. `_requires_python_animation` becomes the
   pipeline's union of family predicates.
3. **Freeze now.** From ratification, no new installer may replace `Scene.play`, `Scene.wait`,
   `_requires_python_animation` or `prepare_animation`. New behavior extends a registered family or waits
   for the pipeline. The dispatch-table drift test gains a ceiling: `Scene.play`'s depth and the count of
   symbols with depth > 1 may fall, never rise, unless this ADR is amended.
4. **Stage 2 (native).** Move the pipeline (normalize, walk, admission memo, family order) into
   `_SceneCore`, with families as native builders plus Python hook sets. Python is called only for hooks a
   user class overrides (§15.2).
5. **Stage 3 (schema).** Generate the class layer's signatures, constructors and refusals from the API
   schema, and split `manimlib_bootstrap.py` into reviewable modules (packaging only, no behavior change,
   proven by the dispatch table and witness registry). The per-import compile of the bootstrap (0.34 s,
   fm-5wq.40) is decided there.

## Invariants every migration step holds

- The witness suites in `scripts/check_portal_runtime.sh` and the embedded suites stay green at every commit.
- `docs/api/portal_dispatch.tsv` changes in the same commit as the behavior, and only in the direction of
  fewer layers.
- Frames of the corpus probe scenes are byte-identical before and after each family moves (the per-family
  witness scene plus the fm-5wq.35 speed-ratio sample's frames).
- No family moves without a counter test for its admission cost: `getattr_static` calls or equivalent per
  play must not grow with family size.

## Consequences

- Makes the behavior of `play` one readable function plus a registration table. Ends the repeated
  per-family admission bugs by giving admission one owner.
- Forbids, after ratification, new wrappers of the play/wait/routing hooks.
- Creates work, filed as children of fm-5wq.15 after ratification, in this order:
  1. the pipeline skeleton with the ten current `play` wrappers' phases registered in today's order;
  2. one child per family moving off its wrapper (fading, movement, rotation, indication,
     update_animations, live_rates, camera_callbacks, scene_execution, playback), each with its counter
     test and dispatch-table delta;
  3. the ceiling in the drift test;
  4. stage 2 and stage 3 epics.
- Removing dead duplicates (`crates/fmn-python/python/animation_semantics.py`, shadowed bootstrap methods)
  still needs the owner's explicit approval per AGENTS.md rule 1; this ADR does not grant it.
